## 二、Windows 插件形态与宿主约束

| 项 | 事实 |
|---|---|
| 产物 | `plugins\lanshare.dll`（位数必须与 `TrafficMonitor.exe` 一致） |
| 显示项 | `IP` = 本机局域网 IPv4；`互通` = 未读总条数；tooltip `秋秋快传 <ip>:<port>` |
| 界面 | 网页 `http://<ip>:<port>/`（服务端**优先读磁盘** `plugins\web\index.html`） |
| 设置弹窗 | 只读：访问地址 / 保存目录 / 记录文件 / 清理天数 / 错误原因；换目录在网页里做 |
| 线程铁律 | UI 线程不许阻塞：`DllMain` 不做事、`DataRequired` 不等锁、`ShellExecuteW` 丢工作线程 |
| 单实例 | 每个实例一把锁；锁失败**不监听**，不静默降级 |
| 消息上限 | **500 条**（内存 + 落盘），超出丢最旧并同步清去重索引 |

## 三、发现与设备表（三端一致的部分）

- announce 字段：`v/app/deviceId/name/port/mac/ips[]/acceptsInbound/filteredNicCount/apiVersion/resumable/platform`。
- 收到 announce 单播回源一发（2 秒限流）；关掉「被发现」后不再广播、不再回应。
- 五态判定：`online / online_no_inbound / unreachable / discovered / offline`，阈值 30 s / 120 s。
- **发送候选不剔 TTL，展示才剔**（否则"一离线就再也发不出去"）。
- 显示名解析：`aliases[会话键]` > 设备 `alias` > `name` > `lastKnownName` > 去 `legacy:` > 「未知设备」。
- 同一台机器按 MAC 认，但**在线的一律不合并**（同机双实例是两个设备）。

## 四、消息与会话

| 项 | 事实 |
|---|---|
| `dir` | **绝对方向**：`in` = 对端发来，`out` = 本端发出 |
| `status` | 只有 `sent` / `failed`，必须由真实投递结果给出 |
| 排序 | `(peerTs, seq, id)`；不用 `recvTs` |
| 幂等 | 同 `msgId` 只入库一次；重发会真的再投一次 |
| 会话排序 | 只按最后一条消息时间（收发即置顶） |
| 清空 | 只清本端记录，不删磁盘文件；`epoch` 按协议递增 |
| legacy | 旧客户端无 deviceId → 必判 `failed`，文案单独处理（"已交给本机…"） |

## 五、文件传输

| 项 | 事实 |
|---|---|
| 上传 | `POST /api/upload`，body 为原始二进制（**不是 multipart**） |
| 单份上限 | **4 GB（三端同源）**；收发都是流式（1 MB 一片），不再整份进内存 |
| 分片大小 | **1 MB**（三端同源；256 KB 时每片一条新连接，实测慢 2–3 倍）；`.part` 落在 `<saveDir>/.~<xid>.part`，收满 `total` 才入库；收齐后用**流式哈希 + rename** 归档 |
| 落盘 | `<saveDir>/<设备名>-<deviceId>/<原名>`；目录名用真实设备名，改名后按 `-<deviceId>` 沿用 |
| 内容去重 | 同目录内"尺寸 + FNV-64"相同 → 复用；同名不同内容才加 `(2)`；**鸿蒙 >2 MB 不做去重**（ArkTS 逐字节哈希约 2.5 MB/s，大文件算哈希会触发 THREAD_BLOCK_6S） |
| 下载 | `GET /api/file?id=&inline=1` |
| 进度 | `GET /api/transfer`：`name/dir/total/received/speed/status/peer` |
| 系统保存 | W：直接写保存目录；H：图片走系统确认，文件走 `DocumentViewPicker`；A：MediaStore / 公共目录 + 扫描 |

## 八、已知限制（不是缺陷，别当 bug 修）

| 限制 | 说明 |
|---|---|
| Windows `fileId → 路径` 是内存态 | 重启后旧消息里的文件取不到（文件仍在磁盘；移动端靠消息表查路径，无此问题） |
| 续传队列只在内存 | 进程被杀后从 0 重传（幂等，不重复上屏）；**传输记录**已落盘，见下一行 |
| 传输记录落盘 | 完成后记录留着、重启还在（`lanshare_transfers.jsonl`）；上次没传完的启动时标「已中断」 |
| 无 HTTP keep-alive | 每片一条新 TCP 连接（`Connection: close`），握手+WiFi 唤醒约 70–130 ms/片；大文件靠 1 MB 片摊薄，仍是下一步优化点 |
| 鸿蒙通知槽位是系统默认 | `NotificationRequest.slotType` / `progress` 与 SDK 类型不兼容，进度用文本条 |
| 鸿蒙后台 ~10 分钟 | 系统 `dataTransfer` 上限，冻结后 socket 不收包 |
| 移动端无消息条数上限 | 只有 Windows 500 条；移动端靠保留期清理 |
| 移动端 MAC 为空 | 普通应用拿不到，显示「未获取」 |
| 无鉴权/无加密 | 同网段知道 `IP:port` 即可读写 |
| OPPO（Android 6）下载目录残影 | 系统 Downloads 里有些记录指向的文件已不在盘上；选中后会明确提示「读取文件失败」（以前是静默无反应） |
| 鸿蒙 debug 包不在系统分享面板里 | 注册信息本身正确（`bm dump` 里 `utd/scheme/maxFileSupported` 与能出现在面板的 WorkBuddy 一致），但 debug 签名包实测不出现在「分享至应用」列表（重启面板进程、重启手机都不行）；release 包不能侧载（9568322），只能等 AGC 上架后复验 |
| 分享进来的文件不复制 | 直接用发送方给的 URI 流式发送（不落盘一份副本），因此发送必须在应用存活期间完成；应用被杀则这次分享作废 |
| 17a 双真网卡合并未验 | 本机只有一张真网卡，环境不满足 |
| 扫码配对未做 | 手动填 IP 已可用 |

## 九、新平台对齐清单

- [ ] `deviceId` 随机生成并落盘，形如 `<前缀>-<12hex>`；**不从指纹派生**
- [ ] `convId` 用同一套 FNV-1a 64 位（**offset basis 少一位**），并用向量自检
- [ ] `msgId = deviceId:epoch:seq`；`seq` 本端全局单调；`epoch` 落盘
- [ ] `dir` 绝对方向；`status` 只两值且由真实投递结果给出
- [ ] `/api/hello` 字段齐全（`deviceId/apiVersion/onlineTtl/staleTtl/acceptsInbound/resumable`）
- [ ] `/api/devices` 五态由服务端算，客户端不派生
- [ ] `/api/messages` 支持 `since` / `wait` / `peer` / 水位二元组
- [ ] `/api/messages/read` 是未读清零唯一入口
- [ ] UDP 8766 announce，字段与本文第三节逐字一致
- [ ] 出站客户端能主动 `POST /api/message` 与 `/api/upload`
- [ ] 上传用原始二进制 + `Content-Length`，**不要 multipart**
- [ ] 文件落盘按 `<设备名>-<deviceId>` + 内容去重 + 同名 `(2)`
- [ ] 接受"在线但不可达"中间态（`onlineTtl < staleTtl`，不得相等）
- [ ] 不静默装系统规则、不假装有防火墙能力
